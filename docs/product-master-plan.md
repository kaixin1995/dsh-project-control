# AI 项目认知与开发控制插件

## 完整功能开发文档 V0.4

---

# 1. 项目背景

随着 AI 编程能力快速提升，开发者越来越多地使用 AI 完成功能开发、Bug 修复、重构、测试和代码 Review。

AI 极大提高了代码生产效率，但同时也带来了新的问题：

* AI 一次可以修改大量代码，开发者很难快速理解所有变化。
* 一个很小的需求，AI 可能修改大量不相关模块。
* 很难确认一次修改真正影响了哪些功能。
* 很难判断当前实现是不是最小侵入方案。
* 很难判断 AI 给出的方案是不是足够合理。
* Git Diff 能看到代码变化，但无法直接说明业务变化。
* AI 说“已经完成”，并不意味着功能真的完成。
* 长时间任务可能因为网络、模型超时等原因中断。
* 高级模型价格高，没有必要让所有简单任务都使用高级模型。
* 项目开发时间越来越长后，很多历史设计原因逐渐遗忘。
* 开发者使用 AI 编写陌生语言时，很容易“功能做出来了，但是代码没有真正学会”。
* 如果插件只记录安装之后的项目历史，那么对于已有多年历史的老项目价值会明显降低。

因此，本插件希望建立一个位于 AI 编程和实际项目之间的长期开发控制层。

---

# 2. 产品定位

插件定位为：

> **面向 AI 编程时代的软件项目认知、变更控制、任务执行、质量核查、历史记忆与开发学习系统。**

它不是单纯的：

```text
AI Code Review 工具
```

也不是单纯的：

```text
AI Coding Agent
```

更不是：

```text
Git 客户端
```

它的核心作用是：

> 让 AI 可以高效率开发，同时保证开发者持续拥有对项目的理解权、判断权和控制权。

---

# 3. 核心目标

插件重点解决六类问题。

---

## 3.1 看懂项目

开发者可以快速了解：

* 项目有哪些核心模块。
* 每个模块负责什么。
* 各模块之间有什么关系。
* 数据从哪里来。
* 数据最终流向哪里。
* 核心业务流程是什么。
* 当前项目有哪些重要约束。
* 哪些模块属于高风险区域。

---

## 3.2 看懂变化

每次 AI 修改完成以后，可以快速知道：

* 改了什么。
* 为什么改。
* 修改了哪些文件。
* 修改了哪些功能。
* 增加了什么行为。
* 删除或改变了什么行为。
* 哪些属于必要修改。
* 哪些可能属于额外修改。

---

## 3.3 看懂影响

帮助开发者明确：

```text
直接影响
间接影响
潜在影响
暂无法确认
```

避免只靠人工阅读 Diff 判断风险。

---

## 3.4 确认 AI 真的完成

不能再采用：

```text
AI：
已经完成全部要求。
```

作为任务完成标准。

而应该形成：

```text
需求
 ↓
计划
 ↓
执行
 ↓
Build
 ↓
Test
 ↓
影响检查
 ↓
Code Review
 ↓
独立验收
 ↓
开发者确认
```

---

## 3.5 保留项目历史

随着项目不断开发，逐渐形成：

* 功能历史。
* 模块演化历史。
* 设计决策历史。
* Commit 历史。
* 风险历史。
* 技术债历史。
* 项目约束。
* 开发原因。

最终可以回答：

```text
为什么这里会这样写？

这个功能什么时候增加的？

当时为什么没有采用另外一种方案？

这个模块历史上发生过哪些重大修改？
```

---

## 3.6 帮助开发者持续学习

AI 不仅负责写代码。

插件还应该帮助开发者真正理解：

* AI 为什么这样写。
* 这种语言为什么采用这种设计方式。
* 某个框架为什么这样使用。
* 这次修改最值得学习什么。
* 自己有哪些知识点频繁遇到但尚未掌握。

# 12. 历史 Change 重建

不能简单采用：

```text
1 Commit = 1 Change
```

因为真实开发中一个功能往往由多个 Commit 组成。

例如：

```text
Commit A
增加 DTO

Commit B
修改 Service

Commit C
补充 API

Commit D
修复编译

Commit E
补测试
```

插件可以判断这些提交很可能属于同一次开发。

然后形成：

```text
Imported Change #18

增加设备离线检测

包含：

Commit A
Commit B
Commit C
Commit D
Commit E
```

---

# 13. 历史 Change 标识

由 Git 历史重建的 Change 必须与插件原生记录区分。

例如：

```text
来源：
Git 历史重建
```

或者：

```text
Imported Change
```

避免开发者误认为：

> 当时插件真实记录过这些内容。

---

# 14. 历史信息可信度

老项目历史必须明确区分：

### 事实

例如：

```text
2025-06-13

OhtService.cs 被修改。

Commit：
fix offline status
```

---

### AI 推断

例如：

```text
AI 推断：

本次修改可能是为了解决
设备离线状态不同步问题。
```

---

### 已确认

开发者人工确认以后：

```text
开发者确认：

此次修改确实用于解决
离线状态同步问题。
```

---


# 31. 已确定冲突检测

```text
不得修改 Kafka Consumer

当前：

OhtKafkaConsumer.cs 已修改
```

操作：

```text
[查看原因]

[撤销相关修改]

[允许本次修改]

[修改已确定]
```

# 47. 最小侵入分析

> AI 是否为了一个小需求改得太多。


# 99. 产品核心原则

## 一切围绕 Change

需求、Plan、执行、Diff、影响、Review、Test、Commit 全部围绕 Change。

---

## 老项目也必须可理解

安装插件之前的历史：

```text
通过 Git 尽可能恢复。
```

安装之后：

```text
通过原生 Change 高精度记录。
```

---

## AI 不能自己宣布成功

Executor 负责执行。

Reviewer 负责审查。

Verifier 负责验收。

开发者负责最终确认。

---

## 证据优先

能通过：

```text
代码

Git

Build

Test
```

验证的内容，不应该单纯依赖模型猜测。

---

## AI 分析必须可追溯

重要结论需要尽量回答：

```text
为什么这样判断？
```

---

## 高级模型用在真正需要的位置

不是所有任务都用最贵模型。

目标是：

```text
便宜模型做机械工作

标准模型做普通开发

高级模型做关键判断

Verifier 做最终核查
```

---

## 开发者永远拥有最终决策权

AI 可以：

```text
分析

开发

建议

Review

验收
```

开发者最终决定：

```text
接受

修改

拒绝

继续

停止
```

# 101. 一句话定义

> **这是一个让开发者在 AI 大量参与软件开发之后，依然能够理解项目过去、掌控项目现在、判断每一次变化，并持续提升自身技术认知的软件开发控制系统。**

最终需要做到：

```text
AI 写得更多，
开发者不是懂得更少，

而是能够借助插件，
更快理解、更准确判断、更长期掌控整个项目。
```
